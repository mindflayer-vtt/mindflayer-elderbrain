# Coordinated appliance release format

Status: metadata verification is implemented in `appliance_release.py`.
Production packaging, downloads, trust-key installation, migration, activation,
rollback and update UI are not implemented by this module. Ordinary startup still
uses the existing build/pull flow until installation can supply prepared images.

A release contains `manifest.json`, detached `manifest.sig`, and
`elderbrain-host.tar.zst`. The host archive holds versioned host tooling, service
templates and migration code, never live configuration or credentials. Extraction
must independently enforce a fixed allowlist and reject unsafe archive members;
a valid signature alone does not authorize arbitrary filesystem replacement.

The format-1 manifest has these exact fields:

| Field | Meaning |
| --- | --- |
| `format`, `kind` | `1`, `mindflayer-elderbrain-release` |
| `version` | Stable coordinated release version (`major.minor.patch`) |
| `platform` | `{os: "ubuntu", release: "26.04", architecture: "amd64"}` |
| `host` | Independent `version`, integer `apiVersion`, and `artifact` |
| `host.artifact` | Fixed `file` name, positive byte `size`, lowercase `sha256` |
| `setup` | Independent `version`, digest-pinned prebuilt `image`, and `hostApi` |
| `setup.hostApi` | Inclusive integer `min`/`max`; must include the coordinated host API |
| `images` | Digest-pinned references for `traefik`, `mindflayer-server`, `foundry` |
| `configurationSchema` | Positive schema version; changes need explicit migration support |
| `notes` | Plain release-note text, not executable markup |
| `downtimeSeconds` | Estimated interruption, shown before consent |

Every image reference includes `@sha256:` and 64 lowercase hex digits. Including
Foundry's image does not provide its licensed application or authorize a download.
The updater must preserve that existing licensing boundary.

Sign the exact manifest bytes using a dedicated appliance release key and
OpenSSL SHA-256 detached signatures (the same primitive already used for verified
serial bundles). The verifier authenticates before parsing, bounds the input,
rejects duplicate/unknown fields, and verifies host archive size and hash without
extracting it. Whitespace changes after signing invalidate the signature.

The appliance release public key must come from a separately trusted installation
or explicit trust-management operation. Never accept a replacement key from the
downloaded manifest/archive, and never reuse the firmware signing private key.
No production appliance signing key is committed or generated by these tests;
test keys exist only in temporary directories.

Full updates require platform/schema compatibility and coordinated Setup/host API
compatibility. Setup-only updates must additionally match the *installed* host
API, not just the host version advertised in the new release. A schema mismatch
currently fails closed; migration support must be implemented before accepting it.

The verifier is not an updater: the next stages must verify staged bytes again,
check operation locks and free space, checkpoint user state, install atomically,
health-check, and retain the previous release for rollback. Signed older metadata
is still cryptographically valid: update ordering, rollback authorization and
replay policy belong in the release-selection/activation coordinator.
